# 좌석 선점 스트레스 테스트 결과 (시나리오 B)

- 작성일: 2026-07-22
- 대상 브랜치: `test/add-k6-performance-test`
- 테스트 스크립트: `k6/scenarios/b-seat-hold-stress.js`
- 관련 문서: [`spike-test-results.md`](./spike-test-results.md) (시나리오 A)
- 상태: **완료** — 조건 5에서 조사 마무리

> 이 문서는 모니터링(OTel+Prometheus+Grafana) 도입 이전 결과(`refactor/seat-lock-redis`,
> 2026-07-10)를 대체한다. 그때 발견한 "높은 rps에서 ECS task가 SIGTERM으로 교체됨" 현상은
> 헬스체크(`/health`)가 비즈니스 요청과 같은 Tomcat 스레드풀을 공유해서 굶은 것이 원인이었다
> (결론은 유효). 이 문제는 헬스체크를 별도 포트로 분리하는 대신 요청 처리 자체의 근본 원인을
> 고치는 방향으로 접근하기로 했다.

## 시나리오 개요

40석을 hold → 즉시 `cancel-hold`로 반납하는 루프로 지속적인 락 경합을 유지하면서,
`ramping-arrival-rate`로 목표 rps를 1 → 100 → 200 → 400 → 800 → 1500까지 계단식으로
올린다(총 3분 20초). 시나리오 A가 "순간 폭증에도 정합성이 깨지지 않는가"를 봤다면, B는
"지속 부하를 얼마나, 어떻게 버티는가"를 본다.

## 측정 기준

- **목표 스케줄 완료율** = 완료 이터레이션 / (완료+드랍+중단). 램프 곡선을 시간에 따라
  적분한 이론상 총 시도 횟수(약 127,000건)와 모든 조건에서 완료+드랍(+중단) 합계가 거의
  정확히 일치했다 — 즉 스케줄 자체(1500rps 구간 포함)는 매번 끝까지 시도됐고, 조건별 차이는
  "그중 몇 %를 실제로 완료했는가"였다. **조건 간 비교는 이 지표를 기준으로 한다.**
- Grafana `HTTP Request Rate` 패널(hold+cancel 합산 원시 req/s)은 표에 참고용으로만
  남긴다 — 목표 램프 곡선의 단위(초당 새 이터레이션 수)와 다르고 Grafana 구간 스무딩의
  영향도 받을 수 있어, 조건 간 비교 근거로 쓰지 않는다.

## 조건별 기록

### 조건 1 — 기준선 (replica=1, DBCP=10, thread=400, CPU 1.5vCPU)

DBCP=10은 시나리오 A 마지막 단계(replica 2대 전제로 줄인 값)를 그대로 둔 채 replica만
1대로 되돌린 상태.

```
목표 스케줄 완료율 75.4% (95,775 / 127,002) · p95 4.04s · dropped 31,227(24.6%)
http_req_failed 80.27%(40석 경합 설계상 정상) · unexpected_error 0
```

- Tomcat 스레드 풀 Busy=400(max)/Idle=0이 ~2분 지속, DB 풀도 max(10)까지 채워짐, **CPU도
  최대 92.9%**까지 상승 — 스레드풀·DB풀·CPU가 거의 동시에 한계에 부딪힘. 시나리오 A(스파이크,
  CPU 최대 11%대)에서는 못 봤던, 지속 부하이기 때문에 나타난 양상.
- 서버 사이드 지연(p95 845ms)과 클라이언트 체감(p95 4.04s) 사이에 큰 격차 확인 — 스레드 풀
  대기가 원인으로 추정.

### 조건 2 — DBCP 10→20 (역효과 확인)

DB 풀만 넉넉하게 열어주면 병목이 CPU/스레드로 완전히 넘어가는지 검증.

```
목표 스케줄 완료율 42.7% (54,239 / 127,002) · p95 1m3s(조건 1 대비 약 15배)
unexpected_error 597 → abortOnFail 임계값 초과로 중도 중단
```

- DB 쪽 지표(Acquisition Time p99 max 1.90s→392ms, Pending 0건)는 의도대로 개선됐지만
  **전체 상황은 오히려 악화**됐다. 테스트 도중 **ECS 컨테이너가 재기동**됨(CPU 패널에 서로
  다른 태스크 2개 등장, Heap Max 라인 점프로 확인).
- 원인: CPU가 이미 부족한(1.5vCPU) 상태에서 DB 풀을 넓히자 더 많은 요청이 동시에 CPU를 놓고
  경쟁 → 경합 심화 → 스레드 풀 완전 포화 → `/health`도 같은 큐에서 굶어 ALB가 컨테이너를
  재기동. **DBCP=10이 의도치 않게 자연스러운 backpressure 역할을 하고 있었다는 뜻.**
- 컨테이너 재기동은 결함이 아니라 정상적인 오버로드 반응으로 해석한다(헬스체크를 분리해서
  이 현상 자체를 없애지는 않기로 함 — 스트레스 테스트의 목적 자체가 "어디서 무너지는가"를
  보는 것이므로 이 결과도 유효한 관측이다).

### 조건 3 — CPU 1.5→3.5vCPU (진짜 상한 확인)

DBCP=20/thread=400은 유지, CPU만 단독 증설(Fargate 제약상 태스크 CPU 2→4vCPU, 메모리도
3GB→7GB로 같이 상승).

```
목표 스케줄 완료율 99.65% (126,563 / 127,002) · p95 270ms
unexpected_error 0, 컨테이너 재기동 없음
```

- CPU 최대 66.9%, Tomcat Busy 최대 130/400 — 스레드 풀·CPU 모두 여유. 서버 사이드 p95
  (92ms)와 클라이언트 p95(270ms) 격차도 거의 해소 — **CPU가 진짜 상한이었음을 확인.**
- 처리량이 커지면서(최대 867 req/s) DB Pending이 순간 최대 97건까지 튐 — 아직 실패로
  이어지진 않았지만 다음 병목 후보로 부상.

### 조건 4 — replica 2대로 확장 (예상 밖 결과)

조건 3과 총 구매 자원(CPU 4vCPU, DBCP 20)을 동일하게 맞춤: 1.5vCPU/DBCP=10 × 2대,
ALB 알고리즘은 기본값(round_robin).

```
목표 스케줄 완료율 82.7% (105,085 / 127,002) · p95 6.9s(조건 1의 4.04s보다도 나쁨)
unexpected_error 0, 컨테이너 재기동 없음
```

- **총 자원이 같은데 조건 3보다 확실히 나쁘다.** 원인은 두 replica 간 부하 불균형 — CPU
  최대치가 89.9% vs 54.9%로 크게 갈렸고, 부하가 쏠린 쪽만 스레드 풀도 포화됐다. DB
  Acquisition Time도 p99 max 2.29s로 조건 3(387ms)보다 훨씬 나쁨 — 로컬 풀이 10개뿐이라
  부하가 쏠린 쪽은 사실상 더 좁은 자원만 쓸 수 있었던 셈.
- ALB 타겟 그룹(`cinema-app-tg`)을 확인한 결과 `load_balancing.algorithm.type=round_robin`
  — 현재 처리 중인 요청 수를 고려하지 않고 기계적으로 배분하는 방식이라, 요청 처리 시간 편차가
  큰 이 워크로드에서 한쪽이 밀리기 시작하면 계속 같은 비율로 요청을 받아 격차가 자기강화적으로
  벌어진 것으로 추정.

### 조건 5 — ALB 알고리즘 round_robin → least_outstanding_requests

조건 4와 설정 동일, 유일한 변경은 ALB 알고리즘.

```
목표 스케줄 완료율 98.8% (125,473 / 127,002) · p95 890ms(조건 4 대비 약 7.75배 개선)
unexpected_error 0, 컨테이너 재기동 없음
```

- CPU 격차가 89.9%/54.9%(35%p) → **74.4%/63.7%(10.7%p)**로 크게 완화됐다 — 알고리즘이
  불균형의 실제 원인이었음을 확인.
- 조건 3 수준(99.65%/270ms)에는 아직 못 미친다 — 남은 격차는 (1) 불균형이 완전히는 안 없어져
  순간적으로 한쪽에 쏠리는 구간이 남아있는 것과, (2) replica당 분할된 DBCP(10)가 두 인스턴스가
  동시에 바빠지자 더 자주 압박받는 것(Pending 최대 386건, Acquisition p99 max 1.77s)으로 추정.

## 핵심 수치 한눈에 보기

| 조건 | 설정 (replica / DBCP / thread max / CPU) | 목표 스케줄 완료율 | p95 | Grafana RPS(참고)† | CPU 최대 | 컨테이너 재기동 |
|---|---|---|---|---|---|---|
| 1. 기준선 | 1 / 10 / 400 / 1.5vCPU | 75.4% | 4.04s | 421 req/s | 92.9% | 아니오 |
| 2. DBCP↑ | 1 / 20 / 400 / 1.5vCPU | 42.7% | 1m3s | 222 req/s* | 91.4% | **예** |
| 3. CPU↑ | 1 / 20 / 400 / **3.5vCPU** | **99.65%** | **270ms** | 750 req/s | 66.9% | 아니오 |
| 4. Replica↑(round_robin) | 2 / 10×2 / 400×2 / 1.5vCPU×2 | 82.7% | 6.9s | 481 req/s | 89.9% / 54.9% | 아니오 |
| 5. ALB 알고리즘↑ | 2 / 10×2 / 400×2 / 1.5vCPU×2 (least_outstanding_requests) | **98.8%** | **890ms** | 684 req/s | 74.4% / 63.7% | 아니오 |

† Grafana RPS는 참고용(단위 불일치·구간 스무딩 가능성)이며 조건 간 비교는 완료율로 한다.
\* 조건 2는 테스트 도중 컨테이너 재기동 구간이 섞여 있어 이 값 자체가 왜곡돼 있다.

## 결론

지속 부하(시나리오 B)에서는 병목이 **DB 풀 → CPU → (replica로 나눌 경우) ALB 라우팅**
순서로 나타났다. 최종적으로 CPU 증설 단독(조건 3, 완료율 99.65% / p95 270ms)이 가장 좋은
결과였고, replica 2대 확장은 ALB 알고리즘을 올바르게 설정했을 때(조건 5) 근접한 수준
(98.8% / 890ms)까지 따라왔지만 완전히 따라잡지는 못했다 — 남은 차이는 인스턴스별로 쪼개진
DBCP 자원 때문으로 추정된다.

## 이후 후보 (조사는 여기서 종료 — 진행하지 않음)

- replica=2 상태에서 인스턴스당 DBCP를 10보다 늘리기 — 조건 5에서 나타난 DB 풀 압박(Pending
  최대 386건) 해소 목적. CPU가 이제 여유 있는 상태(74%/64%)라 조건 2와 달리 역효과 없이
  개선될 가능성이 높아 보이지만, 결과가 자명하다고 판단해 실행하지 않기로 함.
- replica=2 + 인스턴스당 CPU도 증설 — 조건 3과 완전히 동급 자원으로 맞붙여 "풀링 vs 분산"의
  최종 격차를 확인하는 것도 가능하나, 우선순위상 보류.

# 좌석 선점 스트레스 테스트 결과 (시나리오 B)

- 작성일: 2026-07-22
- 대상 브랜치: `test/add-k6-performance-test`
- 테스트 스크립트: `k6/scenarios/b-seat-hold-stress.js`
- 관련 문서: [`spike-test-results.md`](./spike-test-results.md) (시나리오 A, 좌석 정합성 + 튜닝 기록)

> **이 문서는 이전 기록을 초기화하고 다시 작성한 것이다.** 기존 내용(`refactor/seat-lock-redis`
> 브랜치, 2026-07-10 실행분)은 모니터링 스택(OTel + Prometheus + Grafana) 도입 이전에 얻은
> 결과였고, 그때 발견한 "높은 rps에서 ECS task가 SIGTERM으로 교체됨" 현상은 실제 처리 용량
> 한계가 아니라 **헬스체크(`/health`)가 비즈니스 요청과 같은 Tomcat 스레드풀/큐를 공유해서
> 굶은 것**이 원인이었다(결론 자체는 유효). 이 문제는 "헬스체크를 별도 포트로 분리"하는 방식이
> 아니라 요청 처리 자체의 근본 원인을 고치는 방향으로 가기로 결정된 상태이며(관련: 시나리오 A
> 튜닝 기록), 그 결정 이후 모니터링이 갖춰진 지금 환경에서 시나리오 B를 처음부터 다시 측정한다.

## 시나리오 개요

시나리오 A(spike)가 "순간 폭증에도 정합성이 깨지지 않는가"를 봤다면, B는 "요청률을 계단식으로
올렸을 때 어디서부터, 어떻게 무너지는가"를 본다. 40석을 hold → 즉시 `cancel-hold`로 반납하는
루프로 지속적인 락 경합을 유지하면서, `ramping-arrival-rate`로 목표 rps를 1 → 100 → 200 → 400
→ 800 → 1500까지 계단식으로 올린다(각 단계 5~30초, 총 3분 20초). 로그인/CSRF는 시나리오 A와
동일하게 `setup()`에서 미리 끝내고, 측정 구간은 순수하게 홀드+취소 사이클만 반복한다.

시나리오 A의 튜닝(DBCP↑ → Thread↑ → Replica↑)으로 "순간 폭증"에는 강해졌다는 걸 확인했지만,
그 튜닝이 "지속적인 고부하"에도 그대로 유효한지는 별도로 검증이 필요해서 B를 이어서 실행한다.
앞으로 replica 수 / HikariCP 풀 크기 / Tomcat 스레드 수 조합을 바꿔가며 반복 실행하고, 조건별로
아래에 기록을 이어붙인다.

## 조건 1 — replica=1 / DBCP=10 / thread=400 (첫 실행)

### 설정

| 항목 | 값 |
|---|---|
| 앱 컨테이너 | 1.5 vCPU / 3GB (전 조건 공통 고정값) |
| OTel Collector 사이드카 | 0.5 vCPU / 1GB |
| ECS replica | **1개** |
| Tomcat | `threads.max=400`, `min-spare=10`, `accept-count=200` |
| HikariCP | `maximum-pool-size=10` |
| RDS | `db.t4g.micro` (2 vCPU / 1GiB, 버스터블) |

> HikariCP 10은 원래 시나리오 A 마지막 단계에서 "replica 2대로 나눠 쓰는 걸 가정하고" 20에서
> 줄여둔 값이다. 이번 조건은 replica는 1대로 되돌렸지만 DBCP는 그 값을 그대로 둔 상태 —
> 즉 시나리오 A가 끝난 시점의 `application-dev.yml`을 손대지 않고 그대로 실행한 결과다.

### 관찰 (대시보드)

- **HTTP Request Rate (Grafana 패널, hold+cancel 합산 원시 req/s)**: 최대 **421 req/s**
  (평균 105). 이 숫자는 목표 램프 곡선의 단위(초당 새로 시작되는 이터레이션 수)와 다르고
  Grafana 구간 스무딩 영향도 받을 수 있어 "1500"과 직접 비교할 지표는 아니다 — 위에서 계산한
  **74.5% 완료율**이 더 신뢰할 수 있는 근거다.
- **Tomcat Thread Pool (Idle/Busy/Total)**: 약 21:01:30~21:03:30 구간, **Busy=400(=설정
  max) / Idle=0**이 약 2분간 그대로 유지됨 — 워커 스레드가 완전히 바닥남. 시나리오 A(1000VU
  스파이크, 최대 사용량 225/400)에서는 없었던 현상.
- **DB Connection Pool Status**: 같은 시간대에 활성 커넥션이 max(10)까지 채워짐.
  **DB Connection Pending Requests**에 짧게 2건씩 대기가 몇 차례 발생.
  **DB Connection Acquisition Time**: p95 mean 80.7ms/max 533ms, p99 mean 330ms/**max 1.90s**.
- **CPU Utilization (JVM Process)**: 평소 ~0.2% → 부하 구간 **최대 92.9%**까지 상승. 시나리오
  A(스파이크, 최대 11%대)와 확연히 다르다 — 지속 부하가 걸리니 CPU도 실제 병목 후보로 등장.
- **Heap / Old Gen**: 안정적, IHOP 임계치(45%, 1.01GiB) 근처도 안 감 — 메모리 누수 신호 없음.
- **GC 빈도/일시정지**: Minor GC 빈도는 부하 구간에서 최대 0.5 ops/s로 증가했지만, 정지시간
  자체는 p99 기준 98~99ms대로 부하 전후 거의 변화 없음 — GC는 병목이 아님.
- **HTTP Latency (서버 사이드, p95/p99)**: p95 mean 309ms/max 845ms, p99 mean 467ms/max
  1.84s — **k6가 잰 `stress_hold_duration`(p95 4.04s)보다 훨씬 작다.** 시나리오 A에서 확인한
  "서버가 요청 처리를 시작한 이후만 잰 시간과 클라이언트 왕복 시간 사이의 큰 gap"이 이번에도
  재현됨 — 스레드 풀이 바닥난 상태에서 "연결은 됐지만 처리할 워커 스레드를 못 받고 대기"하는
  구간이 이 gap의 상당 부분을 차지하는 것으로 추정.
- **HTTP Error Rate (4xx)**: 평균 33.2%, 최대 96.9% — 좌석 경합 설계상 정상.

### 종합

이번 조건(replica=1, DBCP=10)에서는 **목표 스케줄(1500rps 구간 포함)의 74.5%만 완료했고, 그
과정에서 Tomcat 스레드 풀 · DB 커넥션 풀 · CPU가 거의 동시에 한계에 부딪히는 지점**을 확인했다.
DBCP=10은 애초에 "replica 2대 전제"로 줄여둔 값을 replica 1대에 그대로 적용한 상태라 이 결과가
어느 정도는 예견된 것이지만, 그걸 감안해도 **지속 부하에서는 CPU까지 실제로 밀린다**는 건 시나리오
A에서는 보지 못했던 새로운 발견이다.

| Tomcat | `threads.max=400`, `min-spare=10`, `accept-count=200` (조건 1과 동일) |
| HikariCP | `maximum-pool-size=20` (조건 1의 10에서 변경 — 유일한 변경 변수) |

> 목적: 조건 1에서 CPU/스레드 풀과 동시에 포화됐던 DB 풀을 넉넉하게 열어줬을 때, 병목이
> DB 쪽에서 CPU/스레드 쪽으로 완전히 넘어가는지(=DBCP가 이번엔 진짜로 병목이 아니었는지)를

### 관찰 (대시보드)

- **컨테이너 재기동 확인**: `CPU Utilization` 패널에 서로 다른 두 개의 task 식별자가 시간을
  나눠 나타남(task A `56937bf9-...` 11:40~11:43 CPU 최대 91.4%, task B `7c8e8c11-...`
  11:43~11:46 CPU 최대 63.2%). `Heap Memory Usage`의 최대 힙 라인도 11:45경 ~2GiB→~4GiB로
  점프(새 JVM 프로세스 시작 흔적). ECS 콘솔 태스크 목록에서도 이 시간대에 생성/시작된 태스크가
  "중지됨"으로, 새 태스크가 그 자리를 대체해서 지금 실행 중인 게 확인됨.
- **Tomcat Thread Pool**: 11:42경 Busy=400(=max)/Idle=0까지 찬 직후 11:43에 **모든 지표가
  0으로 뚝 떨어짐**(컨테이너 다운으로 메트릭 수집 자체가 끊긴 것) → 곧이어 Idle=400(완전히 빈
  풀)으로 재시작하는 새 태스크의 궤적이 이어짐.
- **DB 관련 지표는 오히려 조건 1보다 좋아짐**: `DB Connection Pending Requests`는 테스트
  내내 **0** (조건 1은 최대 2건), `DB Connection Acquisition Time`은 p99 mean 162ms/**max
  392ms**(조건 1은 max 1.90s) — DBCP=20이 의도한 대로 DB 쪽 대기는 확실히 해소시켰다.
- **HTTP Latency(서버 사이드)**: p95 max **2.48s**, p99 max **4.55s** — 조건 1(p95 max
  845ms, p99 max 1.84s)보다 훨씬 나빠짐. DB 대기는 줄었는데 서버 사이드에서 잰 지연 자체는
  더 커졌다는 뜻.
- **HTTP Request Rate (Grafana 패널, hold+cancel 합산 원시 req/s)**: 최대 **222 req/s**
  (평균 54.4) — 조건 1(421 req/s)보다 낮게 나왔는데, 이는 처리 능력이 떨어졌다기보다
  **테스트 도중 컨테이너 재기동으로 트래픽을 못 받는 구간이 끼어든 결과**로 보는 게 맞다.
  (이 지표도 조건 1과 마찬가지로 "1500"과 단위가 다른 참고용 수치이며, 완료율 42.7%가
  더 정확한 근거다.)
- **GC**: 빈도는 소폭 증가(Minor 최대 0.345 ops/s)했지만 정지시간은 p99 기준 98~99ms대로
  안정 — 조건 1과 마찬가지로 GC는 원인이 아님.

### 종합

DBCP=20은 의도한 목적(DB 커넥션 대기 해소)은 정확히 달성했다(Pending 0건, Acquisition Time
큰 폭 개선). 하지만 **그 결과로 전체 상황이 개선되기는커녕 훨씬 심각한 지연(p95 4.04s→1m3s)과
컨테이너 재기동까지 발생**했다.

이건 결함이 아니라 **정상적인 오버로드 반응**으로 해석한다: 스레드 풀이 완전히 포화된 상태에서는
`/health`도 같은 큐를 기다려야 하므로, 그 인스턴스가 실제로 "그 순간 요청을 받을 수 없는" 상태가
됐다는 뜻이고 ALB/ECS가 이를 정상적으로 감지해 교체한 것이다. 헬스체크를 별도 포트로 분리하는
방식으로 이 현상 자체를 없애지는 않기로 한다(관련 논의 참고) — 스트레스 테스트의 목적 자체가
"시스템이 어디서, 어떻게 무너지는가"를 보는 것이므로, 이번처럼 무너지는 것 자체가 유효한 관측
결과다.

더 중요한 발견은 따로 있다: **DBCP=10(조건 1)이 의도치 않게 자연스러운 유입 제한(backpressure)
역할을 하고 있었을 가능성이 높다.** CPU가 이미 부족한 상태(1.5 vCPU)에서 DB 풀을 넓혀주면, 동시에
"실제로 CPU 작업을 하려는" 요청 수 자체가 늘어나면서 오히려 CPU 경합이 심해지고, 개별 요청은 더
느려지고, 큐는 더 길어지는 악순환(응답 지연 증가 → 더 많은 요청이 동시에 쌓임 → 지연 추가 증가)에
빠진 것으로 보인다. 즉 **CPU 여유 없이 DBCP만 넓히는 것은 오히려 역효과를 낼 수 있다.**

## 조건 3 — replica=1 / DBCP=20 / thread=400 / **앱 CPU 1.5→3.5vCPU**

### 설정

| 항목 | 값 |

- **Tomcat Thread Pool**: 여전히 한쪽 인스턴스에서 Busy가 잠깐 400(=max)까지 찬 구간이
  보인다 — 불균형이 완전히 사라지진 않았고, 순간적으로는 여전히 한쪽에 쏠릴 수 있다.
- **HTTP Latency(서버 사이드, p95/p99)**: p95 max **1.53s**, p99 max **2.35s** — 조건
  4(p95 max 2.25s, p99 max 3.25s)보다 좋아졌지만, 조건 3(p95 max 387ms)에는 아직 못
  미친다.
- **DB Connection Acquisition Time**: p99 mean 361ms/**max 1.77s** — 조건 4(max 2.29s)보다
  나아졌지만 여전히 조건 3(max 387ms)보다 나쁘다. `DB Connection Pending Requests`도 한
  인스턴스 기준 최대 386건까지 튄 순간이 있었다 — 두 인스턴스가 이제 골고루 바빠지면서, 각자
  10개뿐인 로컬 풀이 오히려 더 자주 시험받는 것으로 보인다.
- **GC**: 빈도는 부하에 비례해 증가(Minor 최대 1.33 ops/s)했지만 정지시간은 여전히 ~96~99ms대로
  안정 — 병목 아님.
- **컨테이너 재기동**: 없었음(사용자 직접 확인).

### 종합

**ALB 알고리즘이 불균형의 실제 원인이었다는 게 확인됐다.** round_robin → least_outstanding_requests
전환만으로 완료율 82.7%→98.8%, p95 6.9s→890ms로 크게 개선됐고, CPU 격차도 35%p→10.7%p로
줄었다. 다만 완전히 조건 3(단일 인스턴스, 99.65%/270ms) 수준까지는 못 미쳤는데, 두 가지가
남은 격차의 원인으로 보인다: (1) 불균형이 완전히는 안 없어져서 순간적으로 한쪽에 쏠리는 구간이
여전히 있고, (2) DBCP가 인스턴스당 10개로 나뉜 상태라 두 인스턴스가 동시에 바빠지면 각자의
로컬 풀이 조건 3의 통합된 20개 풀보다 더 쉽게 압박받는다(Pending 최대 386건).
